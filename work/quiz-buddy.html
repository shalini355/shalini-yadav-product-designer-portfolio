Quiz Buddy

An adaptive programming practice platform designed for students who find LeetCode too punishing and rote multiple-choice quizzes too shallow to matter.

Part 1 · Context & Hook

Programming practice tools fail students in one of two ways.

The first failure mode is too punishing too fast. Platforms like LeetCode assume prior knowledge, offer no scaffolding, and present a blank code editor to a student who has never solved an algorithmic problem before. The message, unintentionally, is: figure it out or leave. Most leave.

The second failure mode is too shallow to matter. Rote multiple-choice quizzes that test whether you can recall syntax from memory do not build the pattern recognition that actual programming requires. Students complete them, score 8 out of 10, and retain nothing.

The gap between these two failure modes is where Quiz Buddy lives. A focused 10-question session. A language the student chooses. A difficulty level that matches where they actually are. A flow that does not punish confusion — it accommodates it.

Part 2 · Constraints & Trade-offs

Three people. Two weeks. One shared repo. No formal handoff.

I took ownership of the UI and question navigation logic. My teammates handled the question database and backend scoring. Every design decision had a coordination cost attached to it.

No design handoff tool

We had no shared Figma seats and no formal design handoff process. Annotated screenshots in a shared Notion doc became the de facto spec. Every component had to be self-explanatory from a static screenshot — I could not rely on interactive annotations to communicate behaviour.

In retrospect this forced a level of visual clarity in the UI that made the final product better, not worse. Constraints that feel like limitations often improve the work.

Schema mismatch — the explanation field

My teammate built the question database schema without a shared alignment session. The explanation field — the text shown in the score review screen explaining why an answer is correct — was marked optional in the schema. I did not know this until I integrated the real question data.

Roughly 40% of questions had no explanation. Without a conditional render, the score review screen showed blank white cards. The fix took 20 minutes. The lesson: define the data contract before designing any screen that displays that data. Every field, its type, and whether it is required or optional — agreed before a single screen is designed.

Component flexibility for edge cases

The question database included three types of questions a standard text card cannot handle: questions with code blocks requiring monospace formatting, questions with images requiring aspect-ratio locking to prevent layout shift, and questions where all four options are correct requiring multi-select behaviour.

Decision: built the question card as a schema-agnostic component. It renders whatever fields exist and degrades gracefully when optional fields are absent. The multi-select case is handled by a type field in the schema that switches the option component between radio and checkbox behaviour automatically.

Feature cuts — hint system and bookmarking

Two features were designed in Figma and cut before development began. The hint system required tracking per-question time-on-screen and a timer component that added complexity disproportionate to its v1 value. The bookmarking feature required a persistent user state layer out of scope for a 2-week timeline.

Decision: shipped the core quiz flow cleanly. Both features are documented as v2 additions with notes on the data model each would require. A cut feature with polished Figma screens is wasted time. A rough feasibility check takes 15 minutes.

Part 3 · Iterations & Key Decision Points

Three decisions that shaped the practice flow.

Decision 1 — Question navigation: linear flow vs. free-jump map

Option A — Strict linear flow

Questions presented one at a time, sequentially. Answer question 1, proceed to question 2. No way to skip. No way to return. Progress shown as a simple step counter.

The rationale for exploring this: simplicity. One decision per screen. No navigation overhead. The user always knows exactly where they are.

Option B — Free-jump question map

A persistent question map showing all 10 questions as numbered tiles. Tiles update state in real time: unanswered, answered, active. Users can jump to any question at any time.

Selected. The question map added approximately 2 hours of development time. It eliminated a critical dead-end in the flow.

During hallway testing with 3 classmates, one specific failure pattern appeared in the linear flow: a student encountered a confusing question, clicked Next without answering, and at question 7 wanted to go back. In the linear flow, there was no back button. The student was trapped — either abandon the session or submit an incomplete attempt. That is a dead end in a product whose entire purpose is to make practice feel achievable.

Decision 2 — Difficulty selector: dropdown vs. descriptive card picker

A standard dropdown with three options (Beginner, Intermediate, Advanced) was faster to build. A card picker with a one-line description of each level took an extra hour.

In hallway testing, 2 out of 3 students selected the wrong difficulty using the dropdown. Both selected Intermediate — not because they were intermediate-level, but because it felt like the safe middle choice. Neither student read the label as a skill descriptor. They read it as a social signal.

After switching to the card picker with descriptions ("Syntax, basic concepts, and first programs" / "Logic, patterns, and data structures" / "Algorithms, optimisation, and system design"), 0 out of 3 students selected a mismatched difficulty. The description gave students permission to select Beginner without it feeling like an admission of weakness.

Decision 3 — Score reveal: per-question feedback vs. end-only

Per-question feedback sounds better in theory. In practice it changes the cognitive mode of the session from quiz (commit to an answer, move forward) to tutorial (second-guess, adjust, learn in place). For a timed practice session designed to simulate exam conditions, end-only scoring keeps the flow intact and the cognitive pressure honest.

Per-question feedback is a legitimate feature — it belongs in a "learning mode" planned for v2, where the user explicitly opts into a slower, more instructional experience. Shipping it in v1 would have blurred the product's core purpose.

Part 4 · Final Solution & Technical Edge

What the prototype covers.

A language selector, a descriptive difficulty card picker, a free-jump question map with real-time tile states, and a conditional score review screen — all built with the data model in mind, not just the visual layer.

Language selector

Six programming languages presented as a card grid. Selecting a language filters the question bank to that language's question set. The component is data-driven — adding a new language requires only a new entry in the question bank JSON, no UI change.

Difficulty card picker

Three descriptive cards as decided in Part 3. Selection confirmed with a visual state change. Proceeds to the quiz on confirmation. One-line descriptions reduced difficulty mismatch in informal testing from 67% to 0%.

Active quiz with free-jump map

Question card in the main area. 10-tile question map persistent at the bottom. Tile states update in real time. Submit button activates only when all 10 questions have been attempted — preventing accidental early submission.

Score review screen

Total score displayed prominently. Per-question review list below, with conditional explanation cards — full card when explanation exists, compact row when it does not. No blank space. No broken layout. Option to retry or return to language selection.

The CS advantage

Three things a non-technical designer would not have caught

The schema-agnostic question card required understanding how the component would consume the data object at runtime — not just how it would look in Figma. The question map state management required understanding the state object driving it: an array of 10 objects each with an id, status, and isActive flag. Designing the visual states without understanding the data structure would have produced a UI that looked right in Figma and broke in the browser. The multi-select edge case required understanding the difference between radio and checkbox input semantics — a one-field schema change that the component handles automatically.

Part 5 · Impact, Hiccups & Honest Learnings

Target metrics and what I would do differently.

This project is not live. These are the metrics that would validate or invalidate the core design decisions if it were deployed.

Session completion Target > 80%
Average session time Target 6–9 min
Difficulty mismatch rate Target < 10%
Day-3 return rate Target > 35%

The schema alignment failure

The explanation field incident is the most instructive failure in this project and the most avoidable. I designed the score review screen assuming every question had an explanation. My teammate built the schema assuming it was optional. Neither of us was wrong within our own context. We were wrong together because we never had a 10-minute alignment conversation at the start of the project. The fix was trivial. The cost of not having that conversation was a near-miss.

The hint system design debt

I designed the hint system in Figma before confirming it was buildable within the timeline. The screens looked good. The feature was cut anyway because the implementation complexity was not evaluated until after the design was done. Evaluate implementation complexity before designing the screen, not after. A 15-minute technical feasibility check at the start of a feature saves hours of design work that gets cut.

The linear flow dead end

The dead-end failure in hallway testing was not a subtle usability issue. It was a fundamental flow failure I had not anticipated because I had not watched a real person use the prototype under realistic conditions. I had tested the flow in my own head, where I never get confused and never want to skip a question. Test with someone who is not you, as early as possible, with the actual clickable prototype.

What I would do differently

Define the data contract first — every field, its type, and whether it is required or optional — before designing any screen that displays that data. Run a feasibility check before designing any feature to high fidelity. And remember: simple means simple for the user, not simple for the developer. The question map made the experience simpler for the user. That is the correct trade-off.
